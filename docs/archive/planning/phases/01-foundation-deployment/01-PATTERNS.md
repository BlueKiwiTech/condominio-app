## Pattern Assignments

Since there are no in-repo analogs, each assignment below points to the exact RESEARCH.md section to copy from verbatim, plus the specific deviations from generic/training-data conventions that matter for this codebase.

### `app/[locale]/layout.tsx` + `components/Providers.tsx` (component/provider, request-response)

**Reference:** `01-RESEARCH.md` → "Pattern 2: Once UI Providers tree" (both code blocks)

Key points the executor must not deviate from:
- CSS import order in the layout is load-bearing: `@once-ui-system/core/css/styles.css` → `@once-ui-system/core/css/tokens.css` → `@/resources/custom.css`, in that order, before any component import.
- Provider nesting order is fixed: `LayoutProvider > ThemeProvider > DataThemeProvider > ToastProvider > IconProvider`. Do not reorder — Once UI's theming cascade depends on this nesting.
- `layout.tsx` is an `async` Server Component because `params` is a `Promise<{ locale: string }>` under Next 16's async-params convention — do not destructure `params` synchronously.

### `next.config.ts` (config, transform)

**Reference:** `01-RESEARCH.md` → "Pattern 2", third code block.

Key points:
- Wrap the config with `next-intl`'s plugin: `createNextIntlPlugin()` wrapping `export default withNextIntl(nextConfig)`.
- `sassOptions: { compiler: "modern", silenceDeprecations: ["legacy-js-api"] }` is required for Once UI's Sass to build cleanly — omitting it is a known build-warning/error source per Once UI's own starter config.
- Do NOT add a `tailwind.config.ts` anywhere in the repo (CLAUDE.md constraint, reinforced by RESEARCH.md Anti-Patterns and State of the Art table — `--no-tailwind` must be passed to `create-next-app`).

### `lib/supabase/server.ts`, `lib/supabase/client.ts`, `proxy.ts` (service + middleware, request-response)

**Reference:** `01-RESEARCH.md` → "Pattern 3: Supabase SSR client helpers" (all three code blocks)

Key points:
- Three distinct files for three distinct execution contexts — never use the browser client (`client.ts`) inside a Server Component, and never use the server client (`server.ts`) inside a Client Component. This is Pitfall 6 in `.planning/research/PITFALLS.md`, still valid per RESEARCH.md.
- The root interceptor file is `proxy.ts` with `export async function proxy(request: NextRequest)` — NOT `middleware.ts`/`export function middleware`. This is a hard correction over what training data or older tutorials would suggest (Next.js renamed this in v16.0.0). If any generated boilerplate (e.g. from `create-next-app` or a Supabase codegen tool) produces `middleware.ts`, rename/rewrite it, or run `npx @next/codemod@canary middleware-to-proxy .`
- Inside `proxy.ts`, call `supabase.auth.getClaims()`, not `getSession()` or `getUser()` — current Supabase guidance for authorization-relevant checks on every request, verified live 2026-09-05. `getUser()` remains valid where a fresh Auth-server round-trip is specifically needed (not this file's job in Phase 1, since there's no auth yet — but wire the helper to the correct pattern now since Phase 2/3 build directly on top of it).
- Env var names inside these three files (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`) must match whatever the actually-created Supabase project issues — see Shared Patterns → "Env Var Naming" below before hardcoding.

### `supabase/migrations/<timestamp>_initial_schema.sql` (migration, CRUD/DDL)

**Reference:** `01-RESEARCH.md` → "Pattern 4: Amended schema + migrations" (full SQL block), cross-checked against `.planning/research/ARCHITECTURE.md` and `docs/handoff-prompt.md`.

Key points — these are corrections layered on top of the original handoff spec, apply all three:
1. **Template/instance split** (`ARCHITECTURE.md` amendment #1): `cuota_templates` (admin-authored definition, no `house_id`) is a separate table from `cuotas` (one row per house per installment, has `house_id`, FK's back to `template_id`). Do not collapse these into one table.
2. **Per-cuota payment rows** (`ARCHITECTURE.md` amendment #2): `payments.cuota_id` is a single FK — one payment row per paid cuota. Multi-cuota payments are represented by multiple rows sharing a `payment_batch_id`, not by an array column or a join table.
3. **`status` is a stored column with only 3 values** (`pending`, `paid`, `advance`) — `overdue` is *never* stored, always computed at query time as `due_date < today AND status != 'paid'` (`ARCHITECTURE.md` Anti-Pattern 2). Do not add `'overdue'` to the CHECK constraint.
4. **D-01/D-02/D-03 from `01-CONTEXT.md` apply directly to this file:** `communities.admin_id` stays nullable, no `NOT NULL` constraint added to it; the migration must NOT insert the ASOBARCELONA community row or any admin linkage — schema/DDL only, zero data-manipulation statements.
5. **Idempotency guard:** `unique (template_id, house_id, installment_number)` on `cuotas` — required per Pitfall 3 in `.planning/research/PITFALLS.md`, load-bearing for Phase 4's cuota-generation logic even though that logic doesn't exist yet.
6. **RLS: enable on all 7 tables, write zero policies.** This is deliberate and complete for this phase, not partial — do not write any `create policy` statements. Verify after applying via `select relrowsecurity from pg_class where relname in (...)` (all true) and confirm `pg_policies` has zero rows for these tables (see RESEARCH.md Validation Architecture).
7. Table field lists not otherwise changed by `ARCHITECTURE.md` (`houses`, `house_residents`, `audit_logs`) should be taken from `docs/handoff-prompt.md`'s original schema — that doc is still the source of truth for fields that weren't part of the corrections.
8. `gen_random_uuid()` needs no extension (native since PG13, Supabase runs PG15+). `pgcrypto` (for future `crypt()`/`gen_salt('bf')` PIN hashing) is Claude's discretion per CONTEXT.md — RESEARCH.md leans toward enabling it now as a cheap forward-looking `create extension if not exists pgcrypto;` statement since this phase already owns "the schema."

## Shared Patterns

### Env Var Naming (applies to: `lib/supabase/server.ts`, `lib/supabase/client.ts`, `proxy.ts`, `.env.example`, Vercel env config)

**Source:** RESEARCH.md Pitfall 3 + Open Question 2 + Code Examples → "Vercel project creation + env wiring"

Supabase is mid-migration from `anon`/`service_role` legacy key names to `sb_publishable_...`/`sb_secret_...` new names. Both work today. **Do not hardcode a naming convention into any file until the Supabase project is actually created and Settings → API Keys is checked.** Whichever naming the created project surfaces, use it consistently across all four surfaces above — never mix `NEXT_PUBLIC_SUPABASE_ANON_KEY` in one file with `..._PUBLISHABLE_KEY` in another. The secret/service-role key must never carry a `NEXT_PUBLIC_` prefix — apply this rule to every file that touches env vars.

### RLS Deny-by-Default (applies to: the migration file only, this phase)

**Source:** RESEARCH.md Pattern 4 + Security Domain section

Enable RLS on all 7 tables (`communities`, `houses`, `house_residents`, `cuota_templates`, `cuotas`, `payments`, `audit_logs`) with zero `create policy` statements in this phase's migration. This is the complete DPLY-02 deliverable — do not partially write policies "just in case." Phase 2 (admin) and Phase 3 (resident) own writing the actual policies once `auth.uid()`-backed sessions and the resident service-role-mediated pattern exist.

### Next.js 16 File Convention Renames (applies to: `proxy.ts` and any generated boilerplate)

**Source:** RESEARCH.md Pitfall 2 + State of the Art table

`middleware.ts`/`export function middleware` is deprecated as of Next 16.0.0. This project's own upstream research docs (`ARCHITECTURE.md`, `PITFALLS.md`, `STACK.md`) were written against a pre-rename mental model and may reference "middleware" — read every such reference as "proxy.ts" for this codebase. If a scaffold or generator produces `middleware.ts`, treat it as a bug to fix, not a valid alternative.
