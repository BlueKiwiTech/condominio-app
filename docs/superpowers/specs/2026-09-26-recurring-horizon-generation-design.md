# Recurring Horizon Generation (Cuotas + Gastos) — Design

**Date:** 2026-09-26
**Status:** Approved by user, ready for implementation planning.

## Purpose

Fixed gastos and recurring cuotas are both meant to be the same concept — "this recurs on a cadence, indefinitely, until someone stops it" — but today they're generated by two inconsistent, unrelated mechanisms:

- **Fixed gastos**: no admin-entered count. Generates zero rows at creation; a daily cron walks forward one period at a time, "catching up to today." Never runs out, but the admin sees nothing until the next cron run.
- **Recurring cuotas**: the opposite. The admin must pick a fixed "Número de cuotas" up front (an arbitrary guess), and *every* installment for every applicable house is generated in one shot at creation. No cron involved at all — the series is finite and stops when the count runs out.

This forces admins to guess a total for something that has no natural end (e.g. "cuota de mantenimiento mensual"), and leaves them looking at a bare one-row schedule for a new gasto until the next day. This design unifies both onto one rolling-horizon model: generate immediately at creation through a computed horizon (so the admin sees a populated schedule right away), then a daily cron keeps extending that horizon forward for as long as the template stays active — no admin-entered count, no upper bound.

## Scope

**In scope:** `condo_expense_templates` rows with `kind='fixed'`; `condo_installment_templates` rows with `installment_type='recurring'` **created after this ships**.

**Out of scope / untouched:**
- Variable gastos (`kind='variable'`) and special cuotas (single or divided) — these represent a known total split across a finite, dated set of installments. They keep generating everything at creation, no cron, no horizon, no admin-visible change.
- Recurring cuota templates that already exist today — left exactly as they are (their fixed count, their already-generated rows). The horizon-cron is structurally unable to see them (see Schema below), so there is no retrofit and no migration risk to existing data.

## Rejected alternatives

- **Retrofitting existing recurring cuota templates into the open-ended model.** Rejected (explicit user decision): no benefit to reinterpreting data admins already reviewed and relied on, and it would need a backfill migration to decide where each legacy series "resumes" from.
- **Duplicating the horizon/generation math inside each create Server Action.** Rejected: the gastos cron already established "the generation function is the single source of truth for how periods are computed" (see its own code comment). Instead, one per-template top-up function per domain is called from two places — the create action (once, for the new template) and the daily cron (looped over every active template) — never two separate implementations of the same math.
- **One unified cron endpoint touching both `condo_expense_templates` and `condo_installment_templates`.** Rejected for the same reason the original gastos design doc rejected merging the two domains' tables: gastos is community-wide, cuotas is per-house — mixing them in one handler buys nothing and makes per-domain failure isolation murkier. Two cron routes, sharing only the horizon formula.

## The horizon rule

```
computeHorizonEnd(today) = max(Dec 31 of today's calendar year, today + 6 months)
```

One formula, used identically by both domains, both at creation and by the cron:

- Created in January → year-end is ~11.5 months out, further than +6 months → generates through Dec 31.
- Created in October → year-end is ~2-3 months out, closer than +6 months → the +6-months floor wins instead, generating further than bare year-end.
- Re-evaluated fresh on every cron run (using that run's "today"), so the target rolls forward every year automatically — no special-cased "new year" logic anywhere, and the horizon never collapses to less than 6 months out no matter when a template was created or how long it's been running.

Implemented once as `computeHorizonEnd(today: Date): Date` in `lib/cuotas/generate.ts` (already the shared pure-math module gastos re-exports from — see `lib/gastos/generate.ts`'s existing `export { splitAmount, toDateOnly, parseDateOnly }`).

## Schema changes

### `condo_installment_templates` (cuotas)

- `number_of_installments` becomes **nullable**. `NULL` = open-ended (new recurring model, horizon-generated). A real integer = the existing finite model — every legacy recurring template and every `special` template (divided or not) keeps its real count, untouched, forever. This mirrors the exact idiom `condo_expense_templates.installment_count` already uses ("null for fixed/indefinite").
- New column: `active boolean not null default true` — mirrors `condo_expense_templates.active` exactly. Lets the admin stop an open-ended template's future generation without deleting its history. Needed because the existing `deleteInstallmentTemplate` action is a hard delete blocked once any payment exists (CUOT-06) — it cannot serve as "pause this series."
- Migration: `alter table condo_installment_templates alter column number_of_installments drop not null;` plus `alter table condo_installment_templates add column active boolean not null default true;`. No data backfill needed — every existing row already has a real `number_of_installments` value, and defaulting `active` to `true` is a no-op for rows the cron will never select anyway (see below).
- The cuotas horizon-cron's query is exactly: `installment_type = 'recurring' AND number_of_installments IS NULL AND active = true`. Legacy recurring templates (`number_of_installments` is a real number) and every special template are structurally invisible to it — no flag to accidentally mis-set, no risk of the cron "catching up" a legacy series past its intended count.

### `condo_expense_templates` (gastos)

No schema change. `active` and nullable `installment_count` already exist and already mean exactly what this design needs.

## Generation mechanics

- **`computeHorizonEnd(today)`** — see above. `lib/cuotas/generate.ts`.
- **`computeNextRecurringDueDate(cadence, lastDueDate)`** — new, `lib/cuotas/generate.ts`. The incremental step for a recurring cuota's next due date, mirroring gastos' existing `computeNextPeriodDate` shape: weekly/biweekly step by `addWeeks(last, 1|2)` with no day forcing; monthly/quarterly/annual step by `addMonths(last, 1|3|12)` with the existing day-1 forcing rule preserved (unchanged from today's `computeDueDates` 'recurring' branch).
- **Cuotas**: new `generateRecurringCuotaInstallments(supabase, template, horizonEnd)` (`lib/actions/cuotas.ts` or a new `lib/cuotas/recurringGeneration.ts`). For one template: finds its last generated `(installment_number, due_date)` across `condo_installments` (or starts from `start_date`/`installment_number=0` if none exist yet — i.e. a brand-new template), then steps forward with `computeNextRecurringDueDate` while `next <= horizonEnd`, inserting **one row per house in `template.applicable_houses`** per new period (cuotas are per-house; this is the one real structural difference from gastos' single-row-per-period shape). Idempotent via the existing `unique(template_id, house_id, installment_number)` constraint (upsert + `ignoreDuplicates`, same pattern as gastos). A `MAX_PERIODS_PER_TEMPLATE` safety cap (same value and reasoning as the existing gastos cron) guards against a malformed cadence never advancing.
  - Called once, synchronously, from `createInstallmentTemplate` right after inserting a new `number_of_installments: null` template (using the admin's own authenticated client) — so the admin's list/preview is populated immediately, not tomorrow.
  - Looped over every matching template by a new daily cron, `app/api/cron/generate-cuotas/route.ts` (service-role client; per-template `try/catch` isolation, same shape as `generate-expenses/route.ts`, protected by the same `CRON_SECRET` bearer check).
- **Gastos**: the existing inline while-loop inside `generate-expenses/route.ts` is extracted into `topUpFixedExpense(supabase, template, horizonEnd)` (`lib/actions/gastos.ts` or `lib/gastos/`). Called the same two ways — once synchronously from `createExpenseTemplate` for `kind: 'fixed'` (a real behavior change: fixed gastos currently generate nothing at creation; this makes their behavior match cuotas' "populated immediately" experience), and looped by the cron, whose stop condition changes from `nextPeriodDate <= today` to `nextPeriodDate <= horizonEnd`.
- `vercel.json` gets a third cron entry: `{ "path": "/api/cron/generate-cuotas", "schedule": "0 6 * * *" }` — confirmed unblocked: Vercel now allows 100 cron jobs per project on every plan including Hobby (the only Hobby restriction is once-per-day scheduling, which this satisfies).

## Admin UI

- **`CuotaFormClient.tsx`**, recurring branch: remove the "Número de cuotas" `Controller` entirely (the field/branch stays exactly as-is for `special` + `is_divided`, unaffected). Add a short explanatory line near the cadence field (new i18n key, both locales) describing the automatic, always-at-least-6-months-ahead generation. The live preview panel switches from "the N installments the admin set" to "the installments that will actually be generated right now" — computed client-side by calling the same `computeHorizonEnd` + due-date-stepping functions the server uses, so the preview can never diverge from the real insert.
- **`CuotasPageClient.tsx`**: add an active/inactive `Badge` plus an Activar/Desactivar button per row, copying `GastosPlantillasPageClient.tsx`'s existing pattern. New Server Action `setInstallmentTemplateActive(templateId, active, locale)` mirrors the existing `setExpenseTemplateActive`. Shown for every row (a harmless no-op for legacy/finite templates, same as gastos already shows the toggle for `variable` templates today) but only meaningfully gates the cuotas cron for open-ended recurring ones.
- New i18n keys under `cuotas` (checked — don't exist yet, unlike `gastos` which already has them): `actions.activate` / `actions.deactivate`, `status.active` / `status.inactive`, and the new recurring-form explanatory copy — added to both `messages/es.json` and `messages/en.json`.
- **`CuotaEditDialog.tsx`**: no change. It's deliberately narrow (name/description/currency/amount only) — active/inactive is a list-level action, not an edit-dialog field.

## Testing

No automated test suite exists anywhere in this repo (consistent with every prior phase in PLAN.md and the gastos design doc) — verification stays manual/behavioral:

- **Idempotency**: invoking either cron twice in the same day must not create duplicate rows (unique constraints + `ignoreDuplicates` guard) — verify via two manual invocations of each cron route.
- **Horizon correctness**: a template created in different months of the year produces the expected end date per the `computeHorizonEnd` formula — verify by creating templates with different `start_date`s and inspecting the generated rows' last `due_date`/`period_date`.
- **Per-house fan-out**: a new open-ended recurring cuota with N applicable houses generates N rows per period, all sharing the same `installment_number` — verify via a direct query.
- **Legacy isolation**: an existing recurring cuota template (real `number_of_installments`) is never touched by the new cuotas cron — verify its installment count is unchanged after running the cron.
- **Active/inactive gating**: deactivating an open-ended template stops the cron from generating further rows for it on the next run, while its existing (already-generated) rows remain untouched and payable.
- **Form behavior**: the create-cuota form no longer shows "Número de cuotas" for `recurring`, but still shows it for `special` + "Dividir en cuotas" — verify visually in both branches.
