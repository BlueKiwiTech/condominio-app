## Screens in Scope

| Route | Purpose | Key states |
|-------|---------|-----------|
| `/[locale]/(auth)/signup` | Admin signup (email + password) | default, submitting, allowlist-rejected, validation error, success → redirect to verify-pending |
| `/[locale]/(auth)/verify-email` | Holding page shown after signup, before email is verified | pending (default), resend-sent confirmation |
| `/[locale]/(auth)/login` | Admin login (email + password) | default, submitting, invalid-credentials error, unverified-email error, success → redirect to dashboard |
| `/[locale]/(auth)/forgot-password` | Request password reset email | default, submitting, sent confirmation |
| `/[locale]/(auth)/reset-password` | Set new password from emailed link | default, submitting, invalid/expired-token error, success → redirect to login |
| any `/[locale]/(admin)/*` route, unauthenticated | Route protection | immediate redirect to `/login` (no flash of protected content) — enforced in `proxy.ts`'s existing `getClaims()` check |

All auth routes render inside a single centered `Card` layout (see Spacing/Layout below), consistent across all five screens for visual continuity.

## Spacing Scale

Declared values (Once UI native tokens, all multiples of 4 — confirmed against `node_modules/@once-ui-system/core/dist/css/tokens.css`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gap inside buttons/links (e.g. spinner + "Signing in…") |
| sm | 8px | Gap between an input's error/helper text and the input itself |
| md | 16px | Default gap between stacked form fields; gap between Heading and subtext in the card header |
| lg | 24px | Card internal padding (all four sides); gap between the form block and the footer link row |
| xl | 32px | Gap between the auth Card and the viewport edge on mobile |
| 2xl | 48px | Vertical padding centering the Card within the page on desktop |
| 3xl | 64px | Not used in Phase 2 (no page-level marketing sections) |

Exceptions:
- **12px** (Once UI `--static-space-12`) for the label-to-input gap within a single field — tighter than the 16px field-to-field rhythm, keeps each label visually bound to its own input.
- No 44px icon-only touch-target exception needed — every interactive element in this phase is a full-width text button or a labeled input, never an icon-only control.

## Typography

Exactly 4 sizes, 2 weights (per Once UI's `body`/`heading` token scale):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`font-size-body-m`) | 400 (normal) | 1.5 (24px, `line-height-body-m`) |
| Label | 14px (`font-size-body-s`) | 400 (normal) | 1.4 (~20px) |
| Heading | 20px (`font-size-heading-m`) | 600 (semibold — Once UI's `font-weight-heading-strong`) | 1.3 (~26px) |
| Caption | 12px (`font-size-body-xs`) | 400 (normal) | 1.3 (~16px) |
| Display | not used in Phase 2 | — | — |

Usage:
- **Body 16/400** — input text, primary paragraph copy (e.g. verify-email holding page body), primary CTA button label.
- **Label 14/400** — form field labels, helper/hint text under inputs, secondary text links ("¿Olvidaste tu contraseña?", "¿No tienes cuenta?").
- **Heading 20/600** — card/page titles only ("Iniciar sesión", "Crear cuenta", "Restablecer contraseña", "Verifica tu correo"). This is the ONLY place weight 600 is used besides the two exceptions below.
- **Caption 12/400** — legal/footnote-style microcopy (e.g. small print under the signup form: "Al continuar aceptas..." if ever added — none required by REQUIREMENTS.md, so this size may go unused; kept in the contract for consistency with future phases, not a Phase 2 requirement).

Weight 600 is additionally used for: the primary CTA button's own label (bold enough to read as the primary action against `solid: contrast`), and the bold lead-in of inline error/success banners (e.g. **"Correo o contraseña incorrectos."** as bold lead sentence, rest of the message at weight 400). No other weight exists in this contract — do not introduce medium(500) or bold(700) anywhere in Phase 2 UI.

## Color

60/30/10 split, expressed as Once UI semantic tokens (auto-resolved by the dark theme in `once-ui.config.ts` — do not hardcode hex in components):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `page` background token (`--page-background` → `neutral-background-weak`, ≈ `#0A0A0A` in dark theme) | Full viewport background behind the centered auth Card on every screen |
| Secondary (30%) | `surface` background token (`--surface-background` → `neutral-background-medium`, ≈ `#151515` translucent) | The auth Card itself; any inline Banner/Feedback container background |
| Accent (10%) | `brand` solid token (`--brand-solid-strong`, blue — ≈ `#2D69FA` family) | **Reserved for:** the primary CTA button fill (Sign up / Log in / Send reset link / Reset password), the focus ring/active border on the currently focused input, and the two inline text links ("¿Olvidaste tu contraseña?" and "¿No tienes cuenta? / ¿Ya tienes cuenta?"). Nothing else in this phase uses brand blue. |
| Destructive/semantic | `danger` solid token (`--danger-solid-medium`, red — ≈ `#E90507` family) | **Reserved for:** the allowlist-rejection message, invalid-credentials error, unverified-email error, expired/invalid reset-token error, and any inline field-validation error text. Never used on a button fill in this phase — there are no destructive actions (delete/remove) in Phase 2. |

Accent reserved for: primary CTA button fill, focused-input border/ring, "forgot password" link, "switch between login/signup" link. Never apply brand blue to body text, card backgrounds, or decorative elements.

## Copywriting Contract

Spanish (`es`) is the default locale (per `next-intl` `localePrefix: 'as-needed'`); English (`en`) is secondary. Both are the source of truth for the message keys the executor will add under an `auth` namespace.

| Element | Copy (es / default) | Copy (en) |
|---------|---------------------|-----------|
| Primary CTA — signup | "Crear cuenta" | "Create account" |
| Primary CTA — login | "Iniciar sesión" | "Log in" |
| Primary CTA — forgot password | "Enviar enlace de recuperación" | "Send reset link" |
| Primary CTA — reset password | "Restablecer contraseña" | "Reset password" |
| Verify-email holding heading | "Verifica tu correo" | "Verify your email" |
| Verify-email holding body | "Enviamos un enlace de verificación a {email}. Ábrelo para activar tu cuenta y acceder al panel de administración." | "We sent a verification link to {email}. Open it to activate your account and access the admin dashboard." |
| Error — allowlist rejection (D-04) | "Este sistema es solo por invitación. Si crees que esto es un error, contacta al administrador de ASOBARCELONA." | "This app is invite-only. If you believe this is a mistake, contact the ASOBARCELONA administrator." |
| Error — invalid login credentials | "Correo o contraseña incorrectos. Verifica tus datos e intenta de nuevo." | "Incorrect email or password. Check your details and try again." |
| Error — unverified email at login | "Tu correo aún no está verificado. Revisa tu bandeja de entrada para activar tu cuenta." | "Your email isn't verified yet. Check your inbox to activate your account." |
| Error — expired/invalid reset link | "Este enlace de recuperación ya no es válido. Solicita uno nuevo." | "This reset link is no longer valid. Request a new one." |
| Success — password reset email sent | "Si el correo existe en nuestro sistema, enviamos un enlace de recuperación." | "If that email exists in our system, we've sent a reset link." |
| Success — password reset complete | "Tu contraseña se actualizó correctamente. Ya puedes iniciar sesión." | "Your password was updated successfully. You can now log in." |
| Destructive confirmation | N/A — Phase 2 has no destructive actions (account deletion/removal begins no earlier than Phase 3) | N/A |

Notes:
- The password-reset-request success message is intentionally non-committal about whether the email exists (standard anti-enumeration practice) — this does **not** contradict D-04, which only applies to the *signup allowlist* rejection (where the user explicitly chose clarity over anti-enumeration hardening for that one specific flow).
- All error copy states the problem, then the next step (never a bare "Error" or raw Supabase error string).
